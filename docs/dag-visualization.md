## 0. 路线与结论

> **推荐路线**：§11 的**传送门节点（方案 C）**。树结构完全不动，把后出现的同态节点标成
> "传送门"叶子（`AliasOf` 指向先出现的规范节点），点它等同于点规范节点，之后的操作挂在
> 规范节点下。规范节点取同态节点里**最深**的一个，出现更深的就立刻换主（§11.3.1）。
> 重复子树从根源消失，而整张图**仍然是一棵树**。
>
> 本文 §3–§10 是**全合并 DAG（方案 B2）**的完整设计，作为 C 的后续演进；
> 两者共用 §4 的走线与 §5 的视觉，C 不需要 §3 的多父模型、§4.6 的商图收缩、§6 的引用规则。

1. **现在为什么不合**：`FindTwin` 只在**当前节点的直接子节点**里找同态节点
   （`App/RewindRuntime.cs:1130` 调用、`:1283` 定义），所以「同一个状态从不同父节点到达」
   一律新建节点。跨分支、跨深度的同态状态永远合并不掉。
2. **不能把判据退化成"只看 checksum"**：`NetFullCombatState` 不含回合流程状态
   （就绪集合、`PlayerTurnPhase`），按下结束回合前后 checksum 相同但语义不同（design.md §4.1）。
   判据分两层：先 `checksum + DeepHash/MergeHash`（逐字节相同），
   不成立再退到 `checksum + 可玩切面`（回合/侧/阶段/就绪，忽略动作编号，见 §11.3.0）。
3. **B2 的代价**：真的把同态节点合并，节点就有多个父，图变成 DAG，折叠、剪枝、多人指纹
   都要跟着改（§4.6、§6、§3.8）。C 用"传送门叶子"绕开了这整套复杂度，逐项对比见 §11.10。
4. **两条路线共用的视觉增量只有三样**：①虚线 + 箭头的合并/传送连线；②被指向的节点加一圈
   细白环；③节点/边 tooltip 与副标题里的计数。圆点编号、六色分支、金色根、焦点白环、
   空心折叠圆、缩放/滚动/拖拽/透明度**全部保持原样**。
5. **前置条件 P0（两条路线都要）**：先修合并键归一化（README 记录的惰性 `CardEnergyCost` 问题），
   否则实机里合并几乎不触发，图上一条边都看不到，方案没法验收。
6. **两个边界情况**：远距离汇聚两条路线都要"走廊 + 底部总线"（§4.4）；子图缩略只有 B2 需要
   商图收缩（§4.6），C 天然不需要——传送门就是叶子（§11.6）。

## 1. 现状复核

### 1.1 合并目前发生在两处

| 位置 | 判据 | 搜索范围 | 结果 |
|---|---|---|---|
| `Capture` 的 `sameState`（`RewindRuntime.cs:1100`） | checksum + `DeepHash`（多人：`Frontier.SameAs` + `SharedDeepHash`） | 只和 `_tree.Current` 比 | 不建点，返回当前节点 |
| `FindTwin`（`:1283`） | 同上；`DeepHash` 不等时用 `Snapshot.MergeHash`（忽略排队动作编号）兜底 | 只搜 `current.ParentId` 的**直接子节点** | `current` 指向那个兄弟 |

### 1.2 "相同校验和却不合并"的三个具体成因

| # | 成因 | 表现 |
|---|---|---|
| 1 | **跨父节点**（主因）：同态节点不是当前节点的直接子节点 | 跳回 #2 换一张牌打出，结果与 #7 同态 → 仍然新建 #12 |
| 2 | **跨分支同深度**：父不同 → `FindTwin` 的循环根本扫不到 | 两条分支各自长出一模一样的子树 |
| 3 | **归一化失败**：结束回合 UI 读到 `CardEnergyCost` 惰性对象，对象图多出缓存节点，`DeepHash` 与 `MergeHash` 都不同 | 连兄弟级合并都会漏；全局化也救不回来 |

> 结论：1、2 靠"全局索引"解决；3 必须单独修（见 §7 P0）。

### 1.3 为什么不能只看 checksum

`checksum` = `NetFullCombatState` 的纯哈希，**不含** `CombatTurnState`：谁已按结束回合、
是否在 PaelsEye 额外回合、侧切换标志都不在里面。所以"按下结束回合前"和"按下后"checksum 相同。
把它们合成一个点，跳过去会拿到"还没按结束回合"的快照 —— design.md §4.1 已经踩过这个坑。
合并键必须是 `checksum`（先筛）+ 深拷贝指纹（再确认）。

### 1.4 现有视觉语法（要原样保住的清单）

| 元素 | 语义 | 实现 |
|---|---|---|
| 32px 圆点 + 编号 | 一个状态节点 | `TreeLayout.NodeDiameter`、`RewindGraphView.DrawNode` |
| 六色循环 + 首子同色 | 分支可区分 | `RewindGraphView.BranchColors`、`TreeLayout.BuildVisible` |
| 金色根 | 战斗开始 | `AccentColor` |
| 白色外环（+5px） | 当前节点 | `DrawNode` 的 `isFocused` |
| 空心圆、不显示编号 | 折叠的子树 | `HollowBox` |
| 直角总线：父竖干 + 半层横段 + 竖段 | 父子关系 | `DrawEdges`（`busY = parentY + LevelHeight*0.5`） |
| 连线可点（热区比线宽大） | 折叠/展开 | `AddEdgeHit` |
| 缩放 = 坐标乘系数后重建 | 不失真 | `RewindHud.ZoomBy` |

### 1.5 现有布局不变量（DAG 必须继续满足）

`tools/UiLayoutTest/LayoutValidator.cs` 已经在守这些，新增几何不能破坏：

1. 任意两个节点圆心距 ≥ 直径 + `SiblingGap`；
2. 第一个子节点与父同 X；其余子节点同高、从左到右；
3. 任意两棵互不包含的子树，Y 区间相交时 X 必须留出间隙；
4. **连线不能穿过任何节点圆**（`CheckSegment`，`:435`）；
5. 画布尺寸 = 内容 bbox + `Padding`，不留多余空白（DAG 版要改成：主干 bbox ∪ 走线 bbox）；
6. 同一份数据重复构建，坐标逐字节一致（刷新不抖动）。

## 2. 目标与非目标

**目标**

- 同一状态只保留一个**可展开的代表**（B2：一个节点；C：一个规范节点 + 若干传送门叶子），
  跨父节点也不会长出第二份子树；
- 合并带来的"我从哪来"不丢失：一眼能看出「这个状态还能从别处走到」；
- 视觉上仍是现在这棵树，老用户不需要重新学习；
- 折叠、跳转、F6、剪枝、缩放、多人协同全部继续可用；
- 合并边在所有既有不变量下"不穿节点、不出画布、位置确定"。

**非目标**

- 不做通用 DAG 编辑器（拖动节点、手工连边）；
- 不做 Sugiyama 那种全局最优分层（会推翻现有布局语义）；
- 不做跨战斗/跨局的全局图（仍然一场战斗一张图）；
- 不做"操作回放"（快照仍是 memento）。

## 3. 数据模型（逻辑层）

> **本章起至 §10 是方案 B2（全合并 DAG）的完整设计。**
> 若采纳 §11 的传送门方案 C，只需要 §4（走线）与 §5（视觉）；
> §3 的多父模型、§4.6 的商图收缩、§6 的引用规则**都不需要**。

### 3.1 主父 + 合并边

节点的 `ParentId` 语义收窄为**主父（spine parent）**：第一次到达该状态时所在的父节点。
它继续承担：布局主干、`F6` 上一节点、剪枝的子树归属、多人树指纹、落盘兼容。

新增**边**这一等公民（挂在 `RewindTree` 上，不是节点上）：

```csharp
sealed class RewindEdge
{
    int From;        // 从哪个节点重放
    int To;          // 命中哪个已存在的同态节点
    string Kind;     // "merge"
    bool Exact;      // true = DeepHash 命中；false = MergeHash 兜底（忽略排队动作编号）
    int Count;       // 同一对 (From,To) 合并了几次
    long LastUtcTicks;
}
```

`ParentsOf(id)` = 主父 + 所有 `To == id` 的边的 `From`。UI 只认这个函数，不直接读 `ParentId`。

**为什么边不放在节点上**：边是图的一等对象（要计数、要时间、要在两个端点都被剪掉时自动消失），
放节点上会让"多父"变成两处真值（`ParentId` 和 `ExtraParents`），剪枝时容易不一致。

### 3.2 全局合并索引

用一个二级索引代替线性扫描（节点几百个时线性也能跑，但合并是每次抓点都做的事）：

```text
byChecksum : Dictionary<uint, List<int>>     // checksum → 节点 id（建点时登记）
byMergeKey : Dictionary<string, List<int>>   // $"{checksum:x8}|{MergeHash}" → 节点 id
```

抓点时先按 checksum 取候选，再逐个 `SameNodeState`（保留现有实现），命中即合并。
候选过滤（顺序执行，任一不满足就跳过）：

1. `node.Playable`（根节点在多人局里是 `Playable=false`，不能把可跳转状态并进去）；
2. `node.Snapshot != null`（内存快照必须还在；跨进程恢复不存在，但剪枝后的残留要防）；
3. `node.State != "stale"`（参与者变化导致的失效节点不能当目标）；
4. `node.Id != current.Id`（同节点走 `sameState` 分支，不需要边）。

### 3.3 捕获结果的四种归宿

```text
抓点 → 算 checksum + 抓 snapshot + 算 frontier
  │
  ├─(A) 与 current 同态 ────────────────► current 不变，不建边（现状保留）
  │
  ├─(B) 命中全局同态节点 t
  │      ├─ t 与 current 存在主干路径关系（祖先 / 后代）
  │      │     ► 不建边，只把 current 指向 t（路径已经连着了）
  │      ├─ 从 t 能到达 current（DAG 可达性守卫，防成环）
  │      │     ► 不建边，只把 current 指向 t，记 link_rejected_cycle
  │      └─ 其它
  │            ► 建 current → t 的合并边（已存在则 Count++ / 刷新时间），current = t
  │
  └─(C) 没有同态 ──────────────────────► 新建节点（现状）
```

注意 (B) 里 **current 会被替换成那个已存在的节点**（通常编号更小，但不保证）：合并后的下一步操作
挂在 `t` 下面，而不是挂在"你刚才所在的分支"。这是语义正确的（状态确实一样），代价是用户会觉得
"我怎么跳走了"。补偿手段就是合并边本身 + 状态栏提示「已合并到 #7（来自 #12）」，见 §5.4。

### 3.4 无环性：证明 + 守卫

**不变量 I1**：合并边 `s → t` 建立时，`t` 一定已经存在（合并的定义）。
**不变量 I2**：状态相等判据只依赖快照内容，与时间、路径无关。
**推论**：若 `t` 是 `s` 的主干祖先，则 `s` 被创建时它的状态就已经等于 `t`，
那时就会命中合并、根本不会创建 `s` —— 矛盾。故合并边不会指向祖先。

所以从"全局合并一开始就生效"的树出发，图天然无环。但为了兼容旧数据（v0.1.11 及以前的兄弟级合并
会留下同态重复节点）和判据演化，仍要两道守卫：

- **路径关系守卫**：`t` 与 `current` 在主干上互为祖先/后代 → 不建边（§3.3 B 第一支）；
- **可达性守卫**：从 `t` 出发（主干 + 既有合并边）能走到 `current` → 不建边，记事件。

守卫触发都写一条 `link_rejected_*` 事件，说明"合并键在不同时刻判出了不一致结果"，值得排查。

### 3.5 编号语义的变化

`id` 仍然是**创建顺序**、单调递增、剪枝不回收。但从此 **id 不再蕴含深度/路径顺序**：
一条来路上可能出现 `#12 → #7`。UI 只显示编号，不显示"第几层"，所以观感不受影响；
文档、MCP 说明和 tooltip 里不要再用"编号越大越靠后"这种说法。

### 3.6 落盘 schema v2

`%APPDATA%\SlayTheSpire2\global_rewind\combat_N\tree.json`：

```jsonc
{
  "schema": 2,
  "next_id": 13,
  "current_id": 7,
  "nodes": [ /* 不变，parent 仍是主父；新增 in_degree 便于排查 */ ],
  "edges": [
    { "from": 12, "to": 7, "kind": "merge", "exact": true, "count": 2,
      "label": "打出 BASH", "last_utc": "2026-11-27T07:21:03Z" }
```

兼容：没有 `schema` / `edges` 的旧文件按"纯树"读（当前 `RewindStore` 只写不读，
这里主要是给外部工具和人工排查用）。`nodes/N.json` 增加 `"parents": [2, 9]`。

### 3.7 MCP

| 工具 | 变化 |
|---|---|
| `rew_tree` | 返回体增加 `links: [{from,to,kind,exact,count}]`，节点增加 `parents`、`in_degree` |

### 3.8 多人

- **只由房主建边**：房主合并后先发 `GrLink { from, to, kind, exact, label, count }`，
  再发既有的 `GrCurrentMessage`（顺序不能反，客户端要在 current 更新前拿到边）。
  客户端只应用，不判定；重复消息按 `(from,to)` 幂等。
- **树指纹必须含边**：`TreeFingerprint()`（`RewindRuntime.cs:2086`）现在只拼
  `id:parent:checksum`，要追加排序后的 `from>to:kind`。否则剪枝握手时两端"看起来一致"，
  实际一边多一条边，删出来的结果不同。
- **剪枝**：DAG 下"剪枝"可能只断一条边（§6）。两端仍按同一份树状态跑同一个确定性函数，
  所以只要指纹包含边就能保证一致；`GrPruneCommit` 的 `removed` 语义扩展为
  `removed_nodes` + `removed_edges` 两个计数。
- **客户端**：`rew_prune`、`rew_capture` 行为不变（客户端本来就不建点、不剪枝）。

## 4. 布局

### 4.1 设计原则

> **树是骨架，合并边是传送门。**

三条硬约束，按优先级：

1. 合并边**不参与** `Measure/Place` —— 加一条边不会移动任何既有节点，刷新不跳；
2. 合并边**不能穿过任何节点圆**（沿用 `LayoutValidator` 的既有不变量）；
3. 走线**完全由数据决定**（同样的树 + 同样的边 → 同样的坐标），不依赖渲染顺序。

合并前后的直观对比（同一段操作，关系示意）：

```text
现在（树：三对节点两两同态，互不相识）      全局合并后（DAG：只留一份 + 一条边）

        ●1                                        ●1
        │                                         │
        ●2                                        ●2
    ┌───┴───┐                                ┌────┴────┐
    ●3      ●6                               ●3        ●6
    │       │                                │         │
    ●4      ●7                               ●4        ●7
    │       │                                │         │
    ●5      ●8                               ●5        ●8
                                             ↑         │
   #6/#7/#8 与 #3/#4/#5 同态                  └─────────┘
   但父不同 → 各长一份                       8 ⇢ 3 合并边（虚线 + 箭头，指向 ●3）
                                              ●3 变成汇聚点（外圈多一道细白环）
```

> 上图只表达关系，不是几何：真实走线绕到目标右侧的兄弟间隙里，见 §4.3。

### 4.2 主干布局：一行不改

`TreeLayout.Build / BuildVisible / Measure / Place` 保持现状：

- `TreeNodeView.Children` 仍然只装**主父子节点**；
- 折叠仍然只作用在主干上；
- 首子同 X、兄弟同高、`SiblingGap` 间距全部照旧。

合并只会**减少**节点（少建一棵重复子树），所以主干通常比现在更紧凑。

### 4.3 合并边的几何

> **已实现的传送门不走这一节**：v0.1.13 起改成了"底部出线、落点在目标上方边中点"的短折线，
> 见 §11.15。下面的七段折线 / 外缘 lane 只服务尚未实现的 B2 合并边。

出口/入口都取"节点侧边"，不在节点正上/正下开口 —— 那里是主干竖干的位置。

**A 档（局部）**的七段折线（默认从右侧走，段号即走线顺序）：

```text
    ● t                     ← 目标（汇聚点）
    ▲
    │  ⑦ 入线 10px（含箭头，指向节点右缘）
  ──┘  ⑥ 收口：t.x + r + 12 处竖直（在兄弟间隙里，不碰节点）
    │
    │  ⑤ 目标相邻带：横移到收口 x（带里没有节点）
    │
    │  ④ lane：跨层竖直（唯一需要 gutter 的一段）
    │
  ──┘  ③ 源相邻带：横移到 lane
    │
    │  ② 竖直落带 42px（= LevelHeight/2，不跨层）
    │
  ● s ──┘  ① 右侧出线 12px（12 < SiblingGap=30，必在兄弟间隙内）
```

规则细化：

| 段 | 位置 | 约束 |
|---|---|---|
| ① 出线 | `(s.x + r, s.y)` → `(s.x + r + 12, s.y)` | 12px < `SiblingGap`，不会碰到右兄弟 |
| ② 落带 | 竖直 `LevelHeight/2`（42px）到**朝目标那一侧**的半层带 | 不跨层；x 在兄弟间隙内，安全 |
| ③ 横移 | 在带内某条轨道上横移到 `laneX` | 带里没有节点（节点只在层线上） |
| ④ 跨层 | `laneX` 竖直 | lane 必须是贯穿该区间的 gutter（§4.4） |
| ⑤ 横移 | 目标相邻带 | 同上 |
| ⑥ 收口 | 目标右侧缝竖直 | `t.x + r + 12`，仍在 `SiblingGap` 内 |
| ⑦ 入线 | 水平 10px + 箭头 | 箭头是合并边唯一的"实心"元素 |

**为什么全直角**：现有渲染器只会用内置 `Control`（`ColorRect` / `Button` / `Panel`），
运行时创建的 C# 节点收不到 `_Draw`，画曲线要么用几十个 `ColorRect` 拼贝塞尔、要么混 `Node2D`，
两者都比直角成本高、且和现有总线风格不一致。**直角 + 虚线 + 箭头已经足够区分**。

**上下对称**：目标在源下方时，②⑤ 用"朝目标那一侧"的带，③④ 方向反过来，其余不变。

### 4.4 走线与通道：两个几何事实

布局本身给两件事作了保证，走线只要利用它们，不需要逐点做碰撞检测：

**事实 1：层与层之间的"带"里没有节点。**
节点只在 `y = 层号 * LevelHeight` 的层线上，两条层线之间（52px 高）是空的。
→ **横移永远在带里做。**

**事实 2：兄弟子树的包围盒在 X 上互不相交（`SiblingGap` = 30），
所以两个相邻兄弟子树之间的空隙是一条从子层一直贯到最深处的"整段竖廊"。**
（`LayoutValidator` 的"任意两棵互不包含的子树在 Y 相交时 X 必须留间隙"就是这个性质。）
→ **长距离竖移走走廊。**

> 一句话：**带里横着走，廊里竖着走。** A 档的"局部 gutter"只是走廊的特例
> （只跨几层、只需在那几层没节点）。

#### 4.4.1 走廊表

```text
Corridors = 每层相邻节点圆之间的空隙（宽 ≥ 30）
            按"能贯通的 y 范围"合并成竖廊
          + 画布左右外缘（贯通全高）
每条走廊: { xMin, xMax, yTop, yBottom }
```

走廊是**区间**不是线：一条走廊里可以并排走多条 lane（`lane = xMin + 6 + k*14`），
用完就换下一条，再不行退到外缘 —— **外缘永远存在，所以任何边都一定画得出来**。

#### 4.4.2 两档路由

| 档 | 触发条件 | 走法 | 段数 |
|---|---|---|---|
| **A 局部** | 源与目标之间最多隔 1 棵兄弟子树，且竖直跨度 ≤ 4 层 | 七段折线（§4.3）：源右缘 → 落带 → 带内横移到目标旁最近的短廊 → 目标相邻带 → 目标右侧缝 → 入线 | 7 |
| **B 跨区** | 隔了 ≥ 2 棵兄弟子树，或竖直跨度 > 4 层 | 源侧走廊 → **横穿段** → 目标侧走廊 → 目标带 | 10 |

B 档的横穿段放哪儿，按方向分两种：

| 方向 | 横穿位置 | 理由 |
|---|---|---|
| 目标比源**浅**（回边，最常见） | 画布**底部总线**：`y = maxY + 24 + k*14` | 树的下方永远是空的，一条横段跨过全部中间子树，零节点、零树线 |
| 目标比源**深**（前进边） | **目标层下方最近的空带**（占满就顺延一条带） | 就近横穿，不必绕到底部；带里只有树线，没有节点 |

```text
        ● 目标 t
        ▲
        │ 入线
      ──┘ 目标带
        │
        │ 目标侧走廊（整段贯通，不碰任何节点）
        │
   ─────┘ 底部总线（回边）或 目标层下方的带（前进边）
────────┘    ← 一条横段横穿中间所有子树
        │
        │ 源侧走廊
        │
      ──┘ 源带
        │
        ● 源 s
```

**为什么回边不放顶部**：顶部是根和 `Padding`，往下生长才是"时间向前"；长线放顶部会和起点抢视觉。
只有一种例外：源与目标都在前两层、且底部总线会让竖直段超过画布高度一半时，才用顶部
（`y = Padding / 2`，规则与底部镜像）。

具体例子（隔两棵子树汇聚的回边）：

```text
        ●3      ●4      ●5      ●6
        │       │       │       │
        ●7      ●10     ●12     ●14
        │       │       │       │
        ●8      ●11     ●13     ●15
        │                       │
        ●9                      ●16
        ▲                        │
        │                        │  源侧走廊（●6 子树外侧的整段空隙）
        │                        ▼
        └────────────────────────┘  底部总线：一条横段从 ●4/●5 下方穿过
```

如果按 A 档在中间横穿，这条线要在某个带里横跨两棵子树、压过若干条树的总线，还很容易被看成
"●5 的一条分支"；B 档只有一条横段 + 两次竖直，两次竖直都落在整段贯通的走廊里。

#### 4.4.3 远距离汇聚的可读性

两条隔得很远的兄弟分支汇聚时，长边会跨过中间几条"无辜"的分支。四件事避免误读：

1. **颜色分层**：A 档线身用目标分支色；B 档线身改中性白（α 0.40），**只在箭头保留目标色**
   —— 免得"跟着一条绿线走，却走进了绿分支"。
2. **过桥断口**：B 档每段底下垫一条 3px 的深色底（画布底色加深，α 0.55），
   跨过树的总线时读作"从上面飞过去"，而不是"在这里接上了"。
3. **悬停隔离**：悬停/点击任意合并边，其它合并边全部降到 α 0.12，这条升到 1.0，
   中间穿多少条分支都不影响追踪。
4. **汇流收口**：同一目标的来边在最后 24px 合并成一段共用收口（`x` 取同一 lane），
   看起来像漏斗收进目标，而不是一堆线各扎一次。（P4 细化，P2 允许先各走各的。）

#### 4.4.4 lane 分配

```text
AllocateLinkRoutes(layout, links):
  corridors = BuildCorridors(layout)          // §4.4.1
  tracks    = 每层带内的横段占用表            // 树的总线占 h/2 处
  lanes     = 已分配 lane 的 (x, yMin, yMax)
  bus       = 底部总线已占用的 (y, xMin, xMax) 列表   // x 区间不重叠可复用同一 y

  foreach link in links 按 (目标 y, 目标 x, 目标 id, 源 id) 排序:
      s', t' = Rep(link.from), Rep(link.to)   // 折叠后的可见代表元，见 §4.6
      if s' == t': 跳过                       // 内部边，不画
      tier = 跨区 ? B : A
      route = tier == A ? RouteLocal(...) : RouteOuter(...)
            // 两档都在候选走廊里按「离端点最近 + y 区间未被占用」挑 lane，
            // 间隔 14px；A 档找不到就升级成 B 档
      输出折线（A 档 7 段 / B 档 10 段）
```

复杂度：`O(E × L × K)`（L = 层数，K = 候选走廊数），E 通常 < 50，可忽略。
排序刻意把**指向同一目标**的边排在一起，lane 相邻、视觉上像"汇流"，也更容易看出哪几条边合并到了同一点。

### 4.5 画布与缩放

- `Width` = max(主干宽度, `max(laneX) + r + Padding`)；走左侧外缘时同时扩展 `minX`。
- `Height` = 主干高度 + **底部总线占用的高度**（`14 * 回边 lane 数 + 24 + Padding`）。
  没有跨区回边时等于现状，一像素都不多。
- 统一平移仍然把"主干最左圆心"对到 `Padding + r`，外缘 lane 和总线只影响画布尺寸，不影响平移基准。
- 缩放继续走"坐标乘系数后重建"，`ScrollContainer` 尺寸与命中区跟着 `CustomMinimumSize` 走，
  与现在完全一致（这也是不能用 `Control.Scale` 的原因，见 design.md §4.3）。

### 4.6 折叠：从"子树"变成"子图收缩"

主干布局没变，折叠的单位仍然是**主干子树**（点树边 → 折叠该子节点的全部主干后代）。
但在 DAG 里，一棵主干子树**不是封闭子图**：被折进去的节点可能还有外部来路，外部节点也可能
把来路伸进去。所以折叠的语义要升级成**子图收缩（quotient）**：

| 概念 | 定义 |
|---|---|
| 折叠区（cluster） | 某个被折叠的节点 + 它的全部主干后代 |
| 可见代表元 `Rep(x)` | `x` 不在任何折叠区里 → `x`；否则沿主父上溯，取**最外层**的折叠根（那个空心圆） |
| 内部边 | `Rep(s) == Rep(t)` 的合并边 → 不画（它在折叠区内部） |
| 边界边 | `Rep(s) != Rep(t)` → 重定向到两个代表元之间，画成一条 |

折叠后的图 = **把每个折叠区缩成一个点之后的商图**。空心圆不再是"叶子"，而是
"一坨节点的代表"，它可以有进有出。

```text
折叠 #3 之前                          折叠 #3 之后（商图）

      ●1                                     ●1
      │                                      │
      ●2                                     ●2
   ┌──┴──┐                              ┌────┴────┐
   ●3    ●6                             ○（#3）    ●6
   │      │                             ▲          │
   ●4    ●7                             │          ●7
   │      │                             │          │
   ●5    ●8                             │          ●8
   │      ╎                             │          ╎
   └──────╎── 8 ⇢ 4（跨进 #3 的子树）   └──────────┘ 8 ⇢ 折叠区
```

注意右图的两点：`#3` 的子树整体收成一个空心圆，但 **8 → 4 那条边没有消失** —— 它被重定向到
空心圆上，tooltip 里仍然能查出真实目标是 `#4`。

> 两幅图都是关系示意，不是几何：真实走线按 §4.3 / §4.4 绕到节点侧边。

#### 4.6.1 边界重定向

| 情形 | 画法 |
|---|---|
| 目标在区里、源在外 | 线画到**空心圆**上，箭头照旧指向圆 |
| 源在区里、目标在外 | 线从空心圆出发 |
| 两端在**不同**的区里 | 线在两个空心圆之间 |
| 两端在**同一个**区里 | 不画（内部边），计入该区的内部链接数 |

聚合：多对真实端点收缩到同一对代表元时，合成**一条**可见边，带 `×N`；tooltip 列出前 3 组真实端点。
空心圆的 tooltip 必须写清"里面是谁"：

```text
折叠区 #3（9 个节点 · 内部 4 条链接）
外部来路 2 条：#12 → #4、#15 → #5
外部去路 1 条：#6 → #8
左键展开 · 点击边可直接定位真实端点
```

#### 4.6.2 商图可能有环，这是显示层的产物

收缩会造出原图里没有的环：折叠区里有两个**互不可达**的分支 `A`、`B`（同一父下的两个兄弟），
外部节点 `X` 合并进 `A`（`X → A`），`B` 又合并出到 `X`（`B → X`）。收缩后就是 `区 ⇄ X`。
原图里并没有环 —— `A` 到 `B` 在区内没有有向路径，只是被"压成一个点"之后接上了。
更长的环同理。**这不影响逻辑层**（§3.4 的无环性针对未收缩的图），但渲染必须接受：

- **自环**（`s' == t'`）→ 丢弃，不当边；
- **双向边**（`s' → t'` 与 `t' → s'` 同时存在）→ 画两条，第二条整体偏移 4px，两个箭头都保留，
  tooltip 标「双向」；
- **平行边**（多对真实端点落在同一对代表元）→ 合成一条带 `×N`。

顺带一提：这也意味着**布局层不能假设"边只从浅指向深"**，A/B 两档路由都必须支持向上和向下。

#### 4.6.3 折叠后的三个计数

空心圆内仍然**不显示文字**（保持现有风格），三类计数全放 tooltip：

| 数 | 含义 |
|---|---|
| `HiddenNodes` | 折叠区里的节点数（= 现有 `SubtreeCount`） |
| `HiddenInternalLinks` | 区内被隐藏的合并边数 |
| `BoundaryIn` / `BoundaryOut` | 穿过边界、被重定向到空心圆的进/出边数（聚合前） |

空心圆的视觉不变；如果 `BoundaryIn + BoundaryOut > 0`，给它加一圈 +3.5px 的**虚线弧环**
（和汇聚点的实线细环区分开），表示"这一坨还有外部的门"。

#### 4.6.4 嵌套折叠

`Collapsed` 仍然按 id 记，展开外层时里层折叠状态原样保留（现状不变）。
收缩取**最外层**代表元，所以嵌套折叠在里层暂时不可见，展开外层后自动恢复，不需要额外状态。

#### 4.6.5 明确不做的三种"子图缩略"

| 方案 | 为什么不做 |
|---|---|
| 可达闭包（隐藏该节点能走到的全部节点） | 在 DAG 里会顺着合并边蔓延到别的分支，一次折叠能吞掉半张图，用户完全无法预期 |
| 支配集（只隐藏"所有路径都必经该节点"的后代） | 图论上最正确，但结果是"折了一半还留一半"，视觉上像坏了；还要额外算支配树 |
| 任意圈选 / 多边形折叠 | 需要把"簇节点"变成图的一等公民（compound graph），布局、折叠、剪枝、多人指纹全部要重做；收益只是"少看几个点" |

折叠单位固定为**主干子树**：只有这个集合能让"布局重排"和"商图收缩"两件事同时成立。

### 4.7 LOD（大量合并时的降级）

| 可见合并边 | 策略 |
|---|---|
| ≤ 32 | 全部正常绘制（虚线 + 箭头） |
| 33 – 96 | 与 current / 悬停节点无关的边：α 0.20，去掉箭头，1px |
| > 96 | 只画与 current / 悬停相关的边，其余完全隐藏；底部状态栏显示「另有 N 条合并边」 |

阈值放在常量里（`LinkBudget` / `LinkHardBudget`），与缩放无关：`zoom < 0.7` 时额外把
非相关边的 alpha 再压 0.1，避免缩小后一片虚线糊住主干。

### 4.8 给 `UiLayoutTest` 增加的不变量

1. 每段折线到任何节点圆心的距离 ≥ `r`（端点段可等于 `r`）；
2. 所有折线点在画布内；画布尺寸 = 主干 bbox ∪ 走线 bbox + `Padding`（不留多余空白）；
3. 同一对**代表元**只有一条可见边；内部边不出现在输出里；
4. 未收缩图上：合并边不指向自己的主干祖先/后代（结构断言，直接从数据算）；
5. 折叠后：每条可见边的两个端点都满足 `端点 == Rep(端点)` 且该端点可见；
   可见边数 = 聚合后的跨边界对数；
6. 所有跨区竖直段都落在走廊里；走廊由 bbox 间隙推导，不与任何节点圆相交；
7. 确定性：同一份数据两次 `Build`，所有坐标完全一致；
8. 性能：500 节点 + 80 条边（其中 20 条跨区），`Build` < 8ms（Release、单线程）。

## 5. 视觉语言

### 5.1 元素对照表

| 现有元素 | DAG 后 | 变化 |
|---|---|---|
| 圆点 + 编号 | 不变 | 无 |
| 六色分支 / 首子同色 | 不变 | 无 |
| 金色根 | 不变 | 无 |
| 白色焦点环（+5） | 不变 | 无 |
| 空心折叠圆 | 外形不变，但不再等于"叶子"：可以被边界边指向 | tooltip 三类计数；有外部边时加一圈虚线弧环 |
| 直角总线 | 不变 | 无 |
| 连线点击折叠 | 树边不变；**合并边点击 = 高亮来路** | 新语义（见 §5.5） |
| 缩放 / 滚动 / 拖拽 / 透明度 | 不变 | 无 |
| —— | **合并边**：虚线 + 箭头（A 档目标分支色 / B 档中性色） | 新增 |
| —— | **汇聚点**：外圈 +3.5px 细白环 | 新增 |
| —— | **折叠区**：边界边重定向到空心圆（商图收缩） | 新语义（§4.6） |

> 方案 C 下，表里的"合并边"读作"传送门 → 规范节点"的连线，样式完全一致（§11.4）。

### 5.2 合并边样式

| 状态 | 线 | 箭头 |
|---|---|---|
| 常态（A 档局部） | 目标分支色，α 0.50，1.5px，虚线 6/5 | 6×6 三角，α 0.80 |
| 常态（B 档跨区） | 中性白，α 0.40，1.5px，虚线 6/5，底下垫 3px 深色（过桥断口） | 6×6 三角，**目标分支色** α 0.90 |
| 悬停 | α 0.95，2px | α 1.0 |
| 最近一次合并（`Recent`） | α 0.95，2px，虚线 8/4 | 8×8 三角，α 1.0 |
| 被点击聚焦 | α 1.0，2px；其余边降到 α 0.15 | α 1.0 |
| LOD 降级 | α 0.20，1px，无箭头 | 无 |

A 档颜色取**目标**节点的分支色（"回到那条分支"），不用源的颜色；B 档线身改成中性白、
只让箭头保留目标色 —— 它要横穿好几条无关分支，染成某一支的颜色反而会误导（§4.4.3）。

方案 C 的传送门连线（`P → A`）完全复用这张表与同一套路由，只是起点换成 22px 的传送门小圆。
虚线用 `ColorRect` 拼接（6px 实 / 5px 空），与现有"线段 = ColorRect"的实现一致。

`Recent` 由 `RewindRuntime` 记：最近一次 `capture_merged` 的 `(from,to)`，写进快照；下次捕获或被跳转打断即失效。
UI 只读，不做时间判断。

箭头实现二选一（P3 验收时定）：`Polygon2D` 三角（一次成型、可旋转指向四个方向）；
或 3 段 2×2 `ColorRect` 拼的台阶形（零新节点类型，但斜边是锯齿）。

### 5.3 汇聚点（in-degree ≥ 2）

- 在圆点外 +3.5px 加一圈细白环：1.2px、α 0.30；悬停时 α 0.55。
- 焦点环仍在 +6px、α 0.85，两者半径与亮度都不同，不会混。
- **方案 C 下判据改成 `PortalCount ≥ 1`**（被几个传送门指向），视觉完全一致。
- **不**用"右下角数字角标"：32px 圆里 7px 的字在 0.5 倍缩放下不可读，
  而编号本身已经在圆内，再加数字会和节点编号打架。
- 如果实机上看不清（P3 验收项），备选方案是"圆点右下 6px 实心小圆点"（像通知角标）。
  两者只做其一，不要叠。

## 6. 剪枝与引用计数

DAG 下"删一个节点"不再等于"删一棵子树"，规则必须写死：

| 情形 | 右键节点 | 结果 |
|---|---|---|
| 只有一个父，且**整棵子树里没有节点带外部来路** | 允许 | 照旧：删节点 + 全部后代 + 落在集合内的边 + 落盘 `nodes/N.json` |
| 节点本身有合并边指向（in-degree ≥ 2） | 拒绝 | 提示「该状态有 3 条来路，先断开多余来路再剪」 |
| 子树里某个节点有外部来路（`#9` 被 `#12` 合并过） | 拒绝 | 提示「#9 还有 1 条外部来路（#12），先断开」——否则会把还能从别处到达的节点删掉 |
| 想删整棵含共享节点的子树 | 两步 | 先右键各条合并边断开，让子树内所有节点都只剩主干父，再右键剪枝 |

**为什么不做"自动改主父"**：主父决定这个节点在树里的列位置。把主父换成另一个来路，
整棵子树会跳到另一列（视觉上"整块搬家"），并且要重算 `Children` 顺序、折叠状态、
多人指纹。收益（少点两下）远小于风险，先不做。

**`CanPruneTarget` 的 DAG 版判据**：

1. 节点存在、`ParentId != 0`（根仍不可剪）；
2. **只沿主干**判断"当前节点是否在待剪子树里"（`PathToRoot` 继续按主父走，
   语义就是"主干路径"，实现不用改，只要改注释）；
3. `ParentsOf(id).Count > 1` → 拒绝，给出合并边条数；
4. 遍历整棵主干子树，任取一个 `ParentsOf(x).Count > 1` 的 `x` → 拒绝，回传第一个这样的节点。

**引用关系**：因为第 3、4 条把"删完还有别的父"的情况都挡在门外，所以不存在悬空节点，
也就不需要真正的引用计数。将来若放开"改主父"，才需要把 in-degree 降级成引用计数。
剪枝时顺手清理 `edges`：`From` 或 `To` 落在被删集合里的边全部删除，并在 `removed_edges` 里计数。

## 8. 测试计划

> 本节按**方案 B2** 写。方案 C 的验收在 §11.11 的表里；布局不变量（§4.8）两条路线共用，
> 只是把"代表元"换成"传送门目标"。

**布局（不启动游戏）**

- `tools/UiLayoutTest` 增加 DAG 生成器：随机树（100–500 节点）+ 10–40 条边
  （含"指向相邻兄弟""跨 2–4 棵子树""目标在源下方"三类），跑 §4.8 的八条不变量；
- 再加四个极端用例：所有边指向同一个目标（汇聚扇入）、所有边跨整张图（全部走底部总线）、
  一半边回一半边去（总线与"目标下方带"混用）、折叠后边界边重定向（商图，含双向边）。

**单机实机（游戏内 dev console + MCP）**

1. **顺序交换**：原分支按 A→B 出两张互不影响的牌，跳回共同祖先按 B→A 出同样的两张
   → 终态逐字节一致 → 不新建节点，出现跨父合并边，`rew_status.merge_hits` +1；
2. **守卫**：跳回 #2 原样重打 #3 那张牌 → 命中 #3（直接子节点），**不建边**，只切 current；
3. 从三条不同分支分别到达同一状态 → 汇聚点 in-degree = 3，tooltip 列 3 条来路，lane 相邻；
4. **跨区汇聚**：让相隔 2 棵子树的左右两条分支汇聚 → 边走 B 档：底部总线只有一条横段、
   两次竖直都落在走廊、不穿任何节点；悬停时其它合并边压到 α 0.12、这条能一眼跟住；
5. **折叠边界**：折叠包含边目标的子树 → 边**重定向到空心圆**（不是消失），tooltip 能查出
   真实端点是区里的哪个节点；点这条边 → 一次展开并定位过去；
6. **内部边**：两端都落在同一个折叠区 → 边消失，空心圆的 `HiddenInternalLinks` +1；
7. **聚合与双向**：两条不同来路折进同一个区 → 合成一条 `×2`；若存在反向边 → 两条各偏移 4px、
   箭头都在，tooltip 标「双向」；
8. 右键合并边断开 → 节点与子树不变，`rew_tree.links` 少一条；右键指向折叠区的边 → 拒绝并提示先展开；
9. 多父节点右键剪枝 → 明确拒绝，文案含来路条数；子树内节点有外部来路时同样拒绝并点名；
10. 跳转到汇聚点 → `rew_verify` 0 不一致、`deep_equal=true`、checksum 等于节点记录值；
11. 长局压测：200+ 节点 + 20+ 边，连续抓点 30 次，面板刷新无可感卡顿。

> 顺序交换在实机上不一定每次都逐字节一致（能力触发顺序、列表顺序都可能不同）。
> P1 阶段先用 MCP 侧可控用例（`rew_test_*` 构造两条路径落在同一 checksum）把边打通，
> 实机只作为"真实场景是否出现合并"的观察项，不作为唯一验收手段。

**多人（双实例 ENet）**

1. 房主合并 → 客户端收到 `GrLink` 且 `current_id` 同步；两端 `rew_tree.links` 逐条相同；
2. 两端 `TreeFingerprint` 相同（含边）；
3. 客户端请求断边 → 被拒绝且文案正确；房主断边 → 两端同时消失；
4. 断边后剪枝握手仍能通过（指纹包含边的增删）。

**回归（每次发版都跑）**

- `tools/Verify`；
- 跳转 == 重放：跳中间节点后 `verify_mismatches=0`、`deep_equal=true`；
- 关闭合并（P1 的开关）后行为与 v0.1.11 完全一致。

## 9. 备选方案

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| **C 传送门节点（§11）** | 不合并：后出现的同态节点标成传送门叶子，`AliasOf` 指向规范节点，点击 = 点规范节点 | 树不变；折叠/剪枝/多人协议几乎不改；实现风险最低 | 节点数仍会涨（每次 +1 叶子）；节点数 ≠ 状态数 | **推荐（P1）** |
| **B1 不合并只标注** | 重复节点保留，节点上加"≡ #3"角标 | 零结构风险 | 节点数继续膨胀；标注在小圆里读不清；"同态"信息弱 | 不解决根本问题 |
| **B2 合并 + 链接边（§3–§10）** | 主干树 + 合并边（多父 DAG） | 节点数 == 状态数、来路不丢、无额外节点 | 需要新布局几何 + 商图折叠 + 剪枝引用 + 新协议 | 备选 / 后续演进 |
| **B3 合并但不画边** | current 直接跳到目标 | 最省事，P1 就能上 | 用户"我明明从 #12 出的牌，怎么到 #7 了"，历史丢失 | 作为 P1 的中间态 |
| Sugiyama 分层 | 全图重排（分层 + 减交叉） | 图论上最规整 | 推翻首子同 X / 兄弟同高的现有语义；折叠失效；实现量大 3–5 倍 | 不做 |
| 力导向 | 弹簧模型 | 好看（对一般图） | 每次刷新位置都变，与"确定性"不变量冲突 | 不做 |
| 缩略图 / 小地图 | 另开一块 DAG 总览 | 不干扰主视图 | 多一层 UI，信息重复，缩放同步麻烦 | 未来可选 |
| 折叠 = 藏边（§4.6 原案） | 端点不可见就把整条边隐藏 | 实现最省 | 折一次就丢掉"这里还有外部来路"；跨区汇聚直接看不见 | 已被收缩方案取代 |
| 任意子图圈选（compound graph） | 把"簇"做成图的一等公民 | 折叠自由度最高 | 布局、折叠、剪枝、多人指纹全部重做，只为"少看几个点" | 不做 |

**为什么推荐 C**：唯一的硬伤是"每次合并多一个叶子"，而它换回来的是**整张图仍然是树**——
布局、折叠、剪枝、多人指纹、`PathToRoot`、`Children` 全部不用动，风险面小一个数量级；
而且 C 可以无损迁移到 B2（传送门 → 边），不会锁死未来（§11.12）。

**为什么保留 B2**：它把"节点数 == 状态数"做干净了，没有传送门带来的视觉噪音与语义分裂。
如果将来传送门数量成为问题，或者要做状态级检索，就按 §11.12 迁移过来——§4/§5 的走线与视觉
是两条路线共用的，迁移只用换数据层。

| 风险 | 影响 | 缓解 |

## 11. 方案 C：传送门节点（推荐）

> 这一章是后加的。命题：**重复状态不合并，而是把后出现的节点标成"传送门"，点击等同于点先出现的节点**。
> 结论：**采纳**，并且它比 §3–§10 的全合并 DAG 更贴合当前代码库。
>
> **实现状态（v0.1.12）**：`AliasOf`、全局规范搜索、最深优先 + 换主、叶子传送门、共享快照、
> 连线/折叠收口、剪枝拒绝、多人 `alias_of` / `demote_old_id` 均已落地；
> `tools/UiLayoutTest` 的 4 个连线场景全绿；**传送门与换主都已在实机复现**（见 §11.14）。

### 11.1 一句话

同一状态仍然可能出现两个节点，但**只有一个能继续展开**：**最深的那个是规范节点（canonical）**，
较浅的都变成**传送门（portal）**，`AliasOf` 指向规范节点。传送门是叶子，永远没有子节点；
点它等于点规范节点，从那以后的操作都挂在规范节点下面。

同态节点**不一定等深度**（一条路多绕几步也能回到同一状态），所以主节点按深度选，
不按出现顺序选：深度相同时保留先出现的，出现更深的就**立刻换主**（§11.3.1）。

于是"重复子树"从根源上消失（不会再长第二份），而整张图**仍然是一棵树**。

```text
        ●1
        │
        ●2
   ┌────┴─────┐
   ●3         ●6
   │           │
   ●4 ≡        ●7
   │           │
   ●5          ●8
               │
               ●9        ← 同态节点里最深的一个 = 规范节点
   #4 ═┈┈▶ #9            （点 #4 = 点 #9）
```

`#4` 是普通节点槽位上的一个小圆（画 `≡`），它记录"从 #3 走出这一步，状态在更深的 #9 也出现过"；
`#9` 因为被传送门指向，外圈加一道细白环。点 `#4` 跳到 `#9`，之后的操作都挂在 `#9` 下面
—— 所以这个状态只会有一份继续展开的子树。`#4` 原来若有子树，换主时会整体移到 `#9` 下。

### 11.2 数据模型

```csharp
// RewindNode 增加一个字段
public int AliasOf;   // 0 = 普通节点；>0 = 传送门，指向规范节点

// RewindTree 增加
int Resolve(int id);                          // 跟随 AliasOf，防御性上限 8 跳
IReadOnlyList<int> PortalsOf(int id);         // 所有 AliasOf == id 的节点
```

| 编号 | 不变量 |
|---|---|
| C1 | `AliasOf` 永远指向 `AliasOf == 0` 的节点（创建时先 `Resolve`，保证只有一跳） |
| C2 | 传送门没有子节点（`current` 永远不是传送门，捕获时父节点必须 `AliasOf == 0`） |
| C3 | 传送门与规范节点**共享同一个 `ObjectGraphSnapshot` 实例**，不复制 memento |
| C4 | 传送门的 `Checksum` / `DeepHash` / `ObjectCount` / `Shared*` 从规范节点复制，不重算 |
| C5 | 传送门占一个正常布局槽位（32px），但只画 22px；`TreeLayout` 一行不改 |
| C6 | **规范节点 = 同态节点里最深的一个**（`Depth` 沿主父链计算）；同深度时保留先出现的那一个 |
| C7 | 出现更深的同态节点时**立刻换主**：旧规范的子节点整体改挂到新规范名下（保持顺序），旧节点清空成叶子传送门，所有指向旧规范的传送门改指新规范 |

C3 是省内存的关键：一次合并只多一个几十字节的节点对象，不多一份几千字段的 memento。
`ObjectGraphSnapshot.Restore()` 只往活对象写值、不改快照本身，所以两个节点指向同一个快照
反复恢复是幂等的、安全的。由此还得到一个免费性质：**跳传送门和跳规范节点恢复的是同一份
memento，`rew_verify` 的结果必然一模一样**。

防御：`Resolve` 遇到悬空 alias（目标不存在，正常不应发生）→ 把该节点当普通节点、`AliasOf` 清 0。

### 11.3 捕获流程

#### 11.3.0 合并判据（实现口径）

| 优先级 | 判据 | 标记 | 说明 |
|---|---|---|---|
| 1 | `checksum` 相同 + `DeepHash` 或 `MergeHash` 相同 | `MergeExact = true` | 逐字节相同，最稳 |
| 2 | `checksum` 相同 + `Frontier.SameStateAs`（回合 / 侧 / 每人回合号 / 阶段 / 就绪集合 / 额外回合） | `MergeExact = false` | 等价同态：差异只在战斗日志、动作编号这类不影响局面的字段 |

为什么需要第 2 层：`CombatHistory` 按顺序记录每一次出牌 / 受伤 / 抽牌。**同样的牌换一个顺序打完、
洗牌后回到同一局面**，checksum 相同、切面也相同，但日志顺序不同 → `DeepHash` 必然不同。
日志不影响可玩状态，跳转时由规范节点的快照整体写回即可。

为什么不直接用 checksum：切面里的阶段 / 就绪 / 额外回合是"玩家能不能操作"的语义，
checksum 不覆盖；结束回合过渡态虽然被建点门禁挡住，多人的就绪集合仍必须比。
`NextActionId / NextHookId / NextChoiceIds` 是给未来动作预分配的编号，不参与第 2 层比较
（快照会把它们整体写回）。

第 2 层命中时，传送门的 tooltip 会写「可玩状态相同（差异只在日志/动作编号）」。


```text
抓点 → checksum + snapshot + 算 frontier
  │
  ├─(A) 与 current 同态 ─────────────► 合并进 current（现状不变）
  │
  ├─(B) 全局找到规范节点 t（跳过 AliasOf != 0）
  │      ├─ B1  t == current ────────► 不变
  │      ├─ B2  t 是 current 的直接子节点 ► current = t（重放同一动作，树边已存在）
  │      ├─ B3  t 与 current 互为祖先/后代 ► current = t，不建传送门（记 portal_skipped_related）
  │      └─ B4  其它：比较深度（dNew = Depth(current)+1，dTwin = Depth(t)）
  │             ├─ dNew <= dTwin ────► 建传送门 P（parent = current，AliasOf = t），current = t
  │             └─ dNew >  dTwin ────► 建普通节点 N，**立刻换主**（§11.3.1），current = N
  │
  └─(C) 没有同态 ────────────────────► 新建普通节点（现状）
```

- **B3 不建传送门**：状态回到祖先说明这一步是"空转"，留一个标记只会增加噪音。
- **B4 先去重**：同一父节点下如果已经有指向 `t` 的传送门，直接 `current = t`，不重复建
  （反复"跳回 C 重放同一动作"只会得到一个传送门）。
- **B4 的 p** 记 `Label`/`Kind` 为触发它的那个动作（"打出 BASH"），tooltip 里读得通。
- 规范化目标仍要过滤：`Playable`、`Snapshot != null`、`State != stale`（同 §3.2）。
- 建立索引：`byChecksum + byMergeKey`（同 §3.2），只是把"建边"换成"建传送门"；
  深度不缓存，沿主父链现算（`O(深度)`，节点数几百时可忽略）。

#### 11.3.1 主节点切换（deepest wins）

```text
dNew <= dTwin                        dNew > dTwin
──────────────                       ─────────────
   (t) 规范                              (t) 旧主 → 传送门（叶子）
    │                                      │
   ...                                    ...
   P ≡ ──▶ (t)                            N  ← 新主（刚建）
                                           │
                                           └─ (t) 原来的孩子整体移过来
```

切换是**一次原子操作**，在同一个 `Capture` 里按固定顺序完成：

1. 正常建节点 `N`（`parent = current`，拿自己的新快照、新编号）；
2. 把旧主 `t` 的 `Children` **整体**移到 `N` 下（保持原顺序，`ParentId` 改成 `N`）；
3. `t.AliasOf = N.Id`、`t.Snapshot = N.Snapshot`（清空成叶子，改为共享快照）；
4. 所有 `AliasOf == t.Id` 的传送门改指 `N`，快照也换成 `N` 的；
5. `CurrentId = N.Id`，落盘 + 广播。

**为什么必须搬孩子**：不搬的话 `t` 会变成"有子树的传送门"，`Prune`、点击语义、悬停提示全要分叉。
搬到新主之后，模型只剩一种非规范节点：**叶子传送门**。

**为什么不会成环**：`N` 不可能落在 `t` 的子树里 —— 若 `current` 是 `t` 的后代，则 `N` 的状态等于
祖先 `t` 的状态，会先命中 B3（空转），根本不会建 `N`。所以第 2 步永远不会把 `t` 的孩子搬进自己的后代。

**代价**：`t` 的子树会跳到 `N` 所在的那一列，视觉上"整块搬家"。换主只在"出现更深的同态节点"时发生，
正常很少见；真频繁发生，说明深度差异确实大，主节点本来就该在更深的位置。

**不级联**：重新挂父会让子树的深度整体变大，但**不回头重算**其它状态组的主节点（否则会连锁搬家）。
`Depth` 每次现算，所以数值始终正确，只是"最深优先"只在建点时判定。见 §11.13。

### 11.4 传送门长什么样

| 元素 | 规格 |
|---|---|
| 槽位 | 32px（布局不变），实际绘制 22px 圆 |
| 圆体 | 空心：`BgColor` 透明、`DrawCenter=false`、边框 1.5px、目标分支色 α0.80 |
| 图标 | 圆心 `≡`，10px，α0.90（字体缺字就退回 `=`） |
| 悬停 | 填充目标色 α0.15（复用 `HollowHoverBox`），同时给规范节点加临时环、连线加亮 |
| 连线 | `P → A` 的虚线 + 向下箭头：从传送门**底部**出线，在空带中线横移，落点是**目标上方那条边的中点**（§11.15） |
| 规范节点 | 被 1 个以上传送门指向 → 外圈 +3.5px 细白环（与 §5.3 的汇聚点视觉一致） |
| `Recent` | 最近一次合并的传送门 + 连线加粗（同 §5.2） |

**为什么不是"虚线圆"**：`StyleBoxFlat` 不支持虚线边框，而现有渲染器只能用内置 `Control`。
"小一号 + `≡`" 已经能和 32px 的折叠空心圆区分开（折叠圆无文字、边框更亮），不需要新渲染技术。

传送门 tooltip：

```text
#9 · 传送门
打出 BASH
≡ #4（状态完全相同）
第 2 轮 / 第 3 回合
左键跳转到 #4 · 右键删除这个传送门
```

副标题计数：`战斗 #1 · 当前 #4 · 12 节点 · 3 传送门`。
统计口径：`SubtreeSize` / 子节点数仍把传送门算作节点（它确实占一个槽位），
tooltip 里注明"含 N 传送门"，避免"节点数和状态数对不上"的困惑。

### 11.5 跳转与导航

| 操作 | 行为 |
|---|---|
| 左键传送门 | `JumpTo(Resolve(id))`，焦点落规范节点；状态栏「已跳转到 #4（来自传送门 #9）」 |
| 右键传送门 | 删除这个传送门（叶子，不碰规范节点） |
| 左键规范节点 | 不变 |
| F7 / `rew_jump_forward` | **跳过传送门**，取第一个非传送门子节点；全是传送门时提示「子节点都是传送门」 |
| F6 / `rew_jump_parent` | 不变（回规范节点的主父） |
| `rew_jump #9` | 解析到 #4，返回体带 `resolved_from: 9` |

**开放问题（P3 决定）**：交叉合并后 `current` 是规范节点 A，F6 回到的是 **A 的主父**，而不是
"你刚才出发的 C"。要不要记 `LastArrivalFrom` 让 F6 优先回到 C？两种都合理：
默认保持现状（F6 = 树上的上一个节点），把"回到出发点"留给点击传送门旁边的树边。

### 11.6 折叠：不需要商图

传送门是叶子，所以：

- 传送门随它所在的父分支一起折叠、展开，**不需要任何新语义**；
- 规范节点在折叠区里 → 连线**单跳收口**到那个空心圆，tooltip 写 `→ 折叠区 #3（内含 #4）`；
- 两端都不可见 → 线隐藏。

上一轮讨论的"子图缩略"（`Rep()`、内部边、平行边、双向边、商图可能有环）在 C 下**全部不存在**。
这是 C 相对 B2 最大的一块减法：§4.6 整章可以不做。

### 11.7 剪枝（v0.1.14：允许删主节点，删完重选）

| 情形 | 行为 |
|---|---|
| 删传送门 | 直接删（叶子），不影响规范节点 |
| 删规范节点 / 含规范节点的子树 | **允许**。子树外的传送门不会悬空：删完立刻重选主节点 |
| 子树内的传送门 | 随子树一起删除，不参与重选 |
| 根节点、当前节点在待删子树里 | 仍然拒绝（与以前一致） |

**重选规则**（`RewindTree.ReelectCanonicals`，与建点同一口径）：

| 子树外还剩几个指向它的传送门 | 结果 |
|---|---|
| 0 | 不用处理（都跟着删了） |
| 1 | 这个传送门**直接转正**（`AliasOf = 0`），变回普通节点 |
| ≥ 2 | **最深**的一个转正（同深度取小 id），其余改指它并共享同一份快照 |

```text
剪 #4 之前            剪 #4 之后（3 个外部传送门）
  #4 (规范)              #5 (规范)  ← 原来最深的传送门转正
  ├─ #6                  #9 ≡ ─┐
  └─ #7                  #12 ≡ ─┼─▶ #5
 #9 ≡ ─▶ #4              #15 ≡ ─┘
 #12 ≡ ─▶ #4
 #15 ≡ ─▶ #4
```

`Depth` 沿主父链现算、同深度取小 id，所以**多人两端重放同一次剪枝会得到同一棵树**，
不需要额外同步消息；树指纹里的 `:alias` 已经把结果覆盖。

为什么不再"先断边再剪"：传送门是"来路"，不是"引用计数"。删掉一片旧分支却要先把每条来路
单独右键一次，操作成本远高于收益；而重选规则是确定性的，语义不会抖。

### 11.8 多人

- 传送门就是普通节点 → 走现有 `GrAnchor`，消息里加 `alias_of`（0 = 普通）。
- 房主建传送门后**先广播 anchor（带 alias），再广播 `GrCurrentMessage`（= 规范节点）**。
- 换主信息跟着锚点走：`GrAnchor` 增加 `demote_old_id`（0 = 普通节点）。客户端在**绑定完新节点之后**
  按 §11.3.1 的第 2–4 步在本地重放同一操作（两端树一致，结果确定），不需要传孩子列表，
  也不需要额外消息与排序保证。传送门则用同一个字段组里的 `alias_of`。
- 客户端只应用，不判定；`Resolve` 本地算。
- 剪枝拒绝的判据两端一致（同一棵树 + 同一份 alias），**不需要新握手**，`GrPruneCommit` 不变。
- `TreeFingerprint` 的每项加 `:alias`，两端对账更严（协议本来就要求同版本）。

相比 B2 需要新增 `GrLink` 消息、指纹含边、断边确认，C 的协议改动只是**一个字段**。

### 11.9 落盘与 MCP

- `NodeDto` / `NodeDigestDto` 加 `"alias_of"`；旧文件缺省 0，按普通节点读。
- `rew_tree` 节点加 `alias_of`、`portal_count`；`rew_status` 加 `portals`。
- `rew_node` 对传送门额外给 `canonical_id`、`canonical_label`。
- `rew_jump` 按 §11.5 解析。

### 11.10 与 B2 逐项对比

| 维度 | **C 传送门（推荐）** | B2 全合并 DAG |
|---|---|---|
| 存储 | 树 + 每节点一个 `AliasOf` | 树 + 边表（节点多父） |
| 每次合并新增 | 1 个叶子节点；**0 份快照**（共享） | 0 节点、0 快照；+1 条边 |
| 图的性质 | 始终是树 | DAG（收缩后还可能有环） |
| 布局 | **完全不变**（传送门占普通槽位） | 主干不变 + 走廊/总线走线 |
| 折叠 | 不变；目标被折叠时单跳收口 | 商图收缩（Rep/内部边/平行边/双向边） |
| 剪枝 | 叶子直接删；目标有外部传送门 → 拒绝 | in-degree 规则 + 子树扫描 |
| 多人 | 现有消息加一个字段 | 新 `GrLink` + 指纹含边 + 断边确认 |
| 主节点选择 | 同态节点里**最深**的一个（同深度保留先出现）；更深者出现时立刻换主 | 无此问题（合并后只有一个节点） |
| 节点数语义 | 节点数 > 状态数（差 = 传送门数） | 节点数 == 状态数 |
| 视觉 | 小圆 `≡` + 虚线到 A；A 双环 | 虚线到 A；A 双环 |
| 实现风险 | **低**（不动树/布局/协议核心） | 高（多父、收缩、环、引用） |
| 适用 | P1 默认 | 传送门膨胀、或需要状态级检索时 |

共用部分：§4 的走线、§5 的视觉、§4.8 的不变量（把"代表元"换成"传送门目标"）。

### 11.11 落地计划（C）

| 阶段 | 内容 | 验收 |
|---|---|---|
| **C-P0** | 合并键归一化（与 B2 同一个 P0） | 实机"跳回 → 重打同一张牌"必须命中合并 |
| **C-P1** | `AliasOf` + 全局规范搜索 + 五归宿 + 深度比较/换主 + 落盘/MCP；UI 先把它画成普通小圆点 | 跨父同态不再长出重复子树；`rew_tree` 能看到 `alias_of` |
| **C-P2** | 传送门视觉（22px + `≡`）+ 连线（复用 §4 路由）+ hover/点击/右键 | 点传送门跳到 A；跨 3 棵子树的连线不穿节点且能一眼跟住 |
| **C-P3** | 折叠收口 + 剪枝拒绝 + F7 跳过 + `Recent` 高亮 | 折叠后连线收口到空心圆；剪枝文案正确 |
| **C-P4** | 多人 `alias_of` / `demote_old_id` + 指纹 + 双实例实测 | 两端 alias / current / 指纹一致 |
| **C-P5**（可选） | LOD（传送门 > N 时降级成小点 + 计数）、槽位收窄 | 长局不糊 |

C-P1 就能独立发版：即使视觉还没做好，用户已经拿到"不再长重复子树"的收益。

### 11.12 什么时候应该升级到 B2

触发条件（满足任一条）：

- 单场战斗传送门长期 > 60，树被小圆点撑宽；
- 需要"节点数 == 状态数"的统计口径；
- 要做状态级检索/去重（比如"这个状态历史上到过几次"）。

迁移代价很低：**每个传送门 → 一条边 `(parent → AliasOf)`，然后删掉传送门节点**，编号留空不回收。
因为视觉层已经共用，迁移只动数据层，不动 §4/§5。

### 11.13 已知代价与开放问题

| 问题 | 说明 / 缓解 |
|---|---|
| 节点数 ≠ 状态数 | 副标题、tooltip 必须明确写出"传送门"三个字，避免排查时误判 |
| 树的宽度会涨 | 每多一个传送门多一个槽位（62px）。缓解：C-P5 的槽位收窄 / LOD |
| 判重仍要抓快照 | 一次合并不省 CPU（只省内存与视觉），这是两种方案共同的前提 |
| 快照共享的引用 | 未来做"快照淘汰"时必须把传送门算作引用，否则会淘汰掉 A 的快照而 B 还在用 |
| 传送门被误当成状态 | 圆内是 `≡` 而不是编号，tooltip 第一行写"传送门"，点击直接跳 A |
| F6 语义 | 见 §11.5 的开放问题，默认保持现状 |
| 剪枝会换主 | 删掉主节点后由"最深的传送门"接任，主节点位置会跳一次；`rew_events` 里记 `prune` |
| 换主时子树搬家 | 旧主的整棵子树会移到新主那一列，视觉上有一次跳变；只在"出现更深同态节点"时发生 |
| 不级联重算 | 重新挂父让子树变深，但不会回头改其它状态组的主节点；极端情况下"最深优先"会暂时不成立，`Depth` 仍然正确 |
| 折叠区内换主 | 换主会把子树移出折叠区，个别隐藏节点会重新出现；不破坏数据，只是观感上突兀 |

## 11.14 实机验证记录（v0.1.12）

**构造方式**（只用打击 / 防御）：第 4 回合按 `S,S,D` 打完并结束回合，敌人行动后进入第 5 回合；
在第 4 回合节点跳回，按 `D,S,S` 再打一遍。两次第 5 回合开始：玩家 73、敌方 12、手牌/牌堆一致，
`checksum = 27da4130`。洗牌用的是游戏自己的 `StableShuffle`（先排序再 Fisher-Yates），
所以弃牌顺序不影响洗牌结果，两条路径的牌堆完全一致。

| 场景 | 结果 |
|---|---|
| 传送门（等深） | `capture_portal portal #21 -> canonical #17 (depth 16 vs 16)`；current 回到 #17，树里只多一个 `≡` 叶子 |
| 换主（更深） | 用测试脚手架把 #17 上移一层（depth 16→15），再重放同一条路径：`capture_canonical_switch node #22 took canon from #17, moved 1 children`；#17 变成 `alias_of=22`，其子节点 #18 改挂到 #22 下 |
| 传送门跳转 | `rew_jump 17` → `requested_id=17, current_id=22`，`verify_mismatches=0` |
| 验收 | `tools/UiLayoutTest` 5/5、4 个连线场景全绿；`tools/Verify` ALL CHECKS PASSED |

**关键前提**：`CombatHistory` 按顺序记录出牌/受伤/抽牌，换序后 `DeepHash` 必然不同。
没有 §11.3.0 的第二层判据（checksum + 可玩切面），这两个节点根本不会合并 —— 这也是最早
"相同校验和却不合并"的真正原因之一。

**测试脚手架**：`rew_test_shrink_depth`（`GLOBAL_REWIND_TEST_HARNESS=1` 才暴露）把节点上移 N 层，
用来制造"更深的同态节点"；它只改树形、不改快照，换主链路仍然走真实的 `Capture` / `DemoteCanonical`。
## 11.15 走线改版（v0.1.13）

> 用户要求：**从下方伸出**，在节点横带的中间空位中点向目标列转向，**落点在主节点上方那条边的中点**。
> 这一版把 §4.3 的七段折线整个换掉；B2 的合并边仍按 §4，但还没有实现。

几何只有三条：

| 段 | 位置 | 说明 |
|---|---|---|
| ① 出线 | `(s.x, s.y + 11)` | 传送门画的是 22px 小圆，从圆的**底部**竖直向下 |
| ② 落带 | `y = s.y + LevelHeight/2 = s.y + 42` | 两行之间空带的**中线**（这一带里没有节点） |
| ③ 跨层 | `x = t.x ± (r + SiblingGap/2) = t.x ± 31` | 目标旁的**空位中点**（兄弟间距 30px 的正中），在这里竖直走 |
| ④ 收口 | `(t.x, t.y - 42)` | 目标**上方那条边的中点**，箭头朝下（`∨` chevron） |
| ⑤ 同层例外 | `(t.x, t.y + 16)` | 源与目标**同一层**时：折线只走**下半层**，到目标正下方直接进圆点，箭头朝上 |

```text
  ● 传送门 s
  ┃ ① 底部出线
  ┗━━━━━━━━━━━━┓        ② 空带中线（y = s.y + 42）
               ┃
        ●──────● 目标  ③ 在目标右侧空位里竖直走
               ▼        ④ 落点 = 上方边中点
```

目标就在下一层时，② 的横段直接走到 `t.x`，落点刚好落在 ④，整条线只有一个直角。
**同层**时走 ⑤：横向段落在下半层（`s.y + 42`），到目标正下方竖直上行 26px 进入圆点下缘——
同层没有"上方那条边"可用（硬要走就得绕过整个圆），所以直接进节点。
空位默认取**右侧**（父总线从左侧过来，右侧干净）；右侧被别的节点占用就换左侧，
再不行退回目标正上方（只在中间层没有节点时成立），最后退回源列——
传送门是叶子，它正下方永远是空的，所以这条兜底一定成立。

**落点为什么是"边"而不是"圆"**：节点正上方必然有一条入边（父节点在正上方，或在总线
`t.y - 42` 处折下来），落在那条边的中点，读起来就是"这个传送门接在这条路径上"；
同时避开节点圆，不用在圆上开口。

**与 §4.3 的差别**：

| | §4.3 七段（B2） | §11.15 新走线（C） |
|---|---|---|
| 出线 | 右侧 12px | 底部 |
| 跨层 | 目标层相邻空位的中点 + 外缘 lane 兜底 | 目标旁空位中点，找不到退源列 |
| 收口 | 目标右缘 + 10px 入线 | 目标上方边中点，箭头朝下 |
| 画布 | 需要按外缘 lane 扩宽 | 不再扩宽（纯主干 bbox） |

**已知取舍**：横段落在空带中线上，会和同一层的树总线**共线**（虚线压在全线之上）。
传送门通常是父节点的最后一个子节点，总线在它左边，所以"向左走"时会共用一段。
这是"中间空位中点"的直接结果；嫌糊就把横段下移 8px（一个常量）。

**测试**：`tools/UiLayoutTest/LinkScenarioTest` 的四个场景改为断言
①起点在传送门底部、②第二点在空带中线、③终点在 `(t.x, t.y - 42)`，
并继续检查不穿节点圆、不出画布、两次构建一致。

## 附录 A · 术语

| 词 | 含义 |
|---|---|
| 主干 / spine | 由 `ParentId` 连成的树；布局与折叠都只作用于它 |
| 合并边 / merge edge | `s → t`：从 `s` 重放一步后状态与已存在的 `t` 相同 |
| 汇聚点 | B2：in-degree ≥ 2；C：被至少 1 个传送门指向（`PortalCount ≥ 1`） |
| 传送门 / portal | 后出现的同态节点，`AliasOf` 指向规范节点；是叶子，点击 = 点击规范节点 |
| 规范节点 / canonical | `AliasOf == 0`、可以继续展开的代表节点 |
| 带 / band | 相邻两层之间的水平区域（高 = `LevelHeight - 直径`），没有节点，横移都在这里 |
| 走廊 / corridor | 由兄弟子树 bbox 间隙形成的整段竖直空地，长距离竖移走这里 |
| gutter | 走廊的局部形态：某一层两个圆之间够宽的空隙 |
| lane | 走廊里的一条竖线（走廊可并排多条） |
| 底部总线 / bus | 画布最下方的横穿通道，给跨区回边用 |
| 折叠区 / cluster | 被折叠节点 + 全部主干后代 |
| 可见代表元 `Rep(x)` | 节点在收缩视图里的代表：自己，或最外层的折叠根 |
| 商图 / quotient | 每个折叠区缩成一点之后的图；可能有自环、双向边 |
| 精确同态 / 等价同态 | `DeepHash` 命中 / 仅 `MergeHash` 命中（忽略排队动作编号） |
